# Decisions

Choices not fixed by the design brief. Each one keeps NaN out and the API small.

- **MSRV 1.85.** First release with edition 2024 and the MSRV-aware resolver; `core::error::Error` (1.81) is available.
- **`LogFloat` arrives in M1, implemented for `f64` only.** The crate is `#![no_std]` from day one, so math has to be routed through a trait anyway; M3 adds `f32` instead of rewriting M1.
- **`checked_mul` / `checked_div` return `Option`, not `Result`.** It matches `checked_sub` and the standard library's `checked_*` convention; there is only one failure reason for each.
- **∞/∞ is indeterminate, like 0/0.** `inf - inf` in the stored log is NaN, and either answer (0, 1, ∞) would be a guess.
- **`powf` follows IEEE `pow` for 0⁰ = ∞⁰ = 1ᵖ = 1 and panics on a NaN exponent.** These are the only cases where `p · ln` would be NaN.
- **`-0.0` is never stored by checked constructors or by arithmetic.** `from_ln(-0.0)` and `ONE.recip()` store `+0.0` so `Debug` and bit-level comparisons are unsurprising.
- **No `TryFrom<F> for Log<F>`.** `try_from_value` is the one fallible constructor; a trait impl would be a second spelling of it.
- **No `Ord` wrapper.** `total_cmp` covers sorting and `max_by`; a wrapper type would add surface for little gain.
- **`try_to_value` returns `None` only when the result rounds to 0 or ∞.** Subnormal results are returned (with reduced precision) because `F` can represent them.
- **`log(base)` panics on a base that is not finite, positive and ≠ 1.** Every such base would make the result NaN or meaningless.
- **`max` / `min` are provided.** Max-product (Viterbi) code needs them and `PartialOrd` alone does not give them.
- **`Log::ZERO` needs a type annotation (`Log::<f64>::ZERO`).** Rust does not use default type parameters for inference; this is a language limitation, not a choice.
- **`log1mexp` is a public free function on raw floats and panics for d < 0 or NaN.** It is useful on its own (it is the kernel of subtraction), and returning NaN would break the crate's NaN policy.
- **The log-sum-exp accumulators leave one copy of the maximum out and finish with `m + ln_1p(s)`.** Adding the maximum's `exp(0) = 1` first would round away the low bits of small corrections.
- **`sum_two_pass` and `product_compensated` are associated functions** (`Log::sum_two_pass(&xs)`), so they do not need an extension trait.
- **`Sum`/`Product` are also implemented for `&Log`,** so `slice.iter().sum()` works without `.copied()`.
- **Literals sometimes need a suffix (`Log::from_value(5.0_f64)`).** With two `LogFloat` impls, a bare float literal is ambiguous when a method is called on the result before inference settles.
- **No `alloc` feature.** None of the slice utilities allocates (they work in place or reduce), so they are available everywhere; a feature that gates nothing would be noise.
- **Raw-log slice functions do not validate input.** NaN in gives NaN out (reductions) or `None` with the slice untouched (in-place functions); validating every element would cost a pass for data that is normally clean.
- **In-place normalisers return `Option` of the normaliser.** The normaliser is what a scaled forward algorithm accumulates, and `None` (with the slice untouched) covers the empty / all-zero / infinite cases without NaN.
- **Zero weights exclude their term in weighted means,** even if the value is infinite; that is what a weight of zero means, and it avoids 0·∞.
- **`SignedLog` stores zero with a positive sign,** so there is no −0 and `==`, ordering and `TryFrom<SignedLog> for Log` behave without special cases.
- **A non-zero `SignedLog` divided by zero is an infinity with the numerator's sign,** because zero carries no sign.
- **`SignedLog`'s `Sum` accumulates positive and negative terms separately and subtracts once,** so cancellation happens once rather than at every sign change.
- **`SignedLog` has no powers or roots.** Fractional powers of negative numbers leave the reals; take them on the magnitude.
- **`Display` inside the float's normal range prints the float itself** (positional, like `f64`), as the brief asks; outside it prints scientific notation from the stored log. Subnormal values count as outside, so `5e-324` prints all the digits its log resolves rather than the float's three.
- **Without a precision flag, beyond-range `Display` prints the shortest mantissa that parses back to the same `Log`.** This mirrors Rust's float formatting and makes `parse(display(x)) == x` exact.
- **`FromStr` uses the float's own parser inside the normal range** (|exponent| ≤ 307 for `f64`, 37 for `f32`), so parsing agrees exactly with `from_value`; beyond it, `ln(m) + k·ln 10` in double-double.
- **Out-of-range strings saturate rather than error** (`"1e<400 nines>"` parses to `INFINITY`), matching float parsing.
- **`log2`, `log10`, `from_log2`, `from_log10` use double-double constants.** With a plain product, `from_log10(90000.0)` was 2·10⁻¹¹ off and displayed as `1.00000000002e90000`; with it, it prints `1e90000`.
- **`LogDisplay` ignores width and fill;** the precision flag applies to the exponent, which is the part a reader wants to control.
- **`ParseLogError` is opaque** (no public kind enum); its message distinguishes empty, invalid, negative and NaN input.
- **serde: infinite stored logs are strings (`"-inf"`, `"inf"`) in human-readable formats.** JSON writes infinities as `null`, which would make `Log::ZERO` unreadable; binary formats keep the raw float.
- **`SignedLog` serializes as a `(negative, ln)` tuple,** reusing `Log`'s representation for the magnitude.
- **`serde_as_value` writes numbers in range and scientific strings beyond it,** so in-range data stays readable by other tools while 1e-5000 survives.
- **num-traits: `Bounded::max_value()` is `INFINITY`.** It is the greatest `Log`; a finite "largest" value would be arbitrary. `Num`, `Float`, `Signed`, `ToPrimitive` and `CheckedSub` are not implemented because their contracts assume subtraction, negatives or exact conversion. `SignedLog` gets `Zero` and `One` only.
- **approx compares stored logs and treats identical infinities as equal,** since the float impls compute ∞ − ∞ = NaN and would report `ZERO != ZERO`.
- **bytemuck impls are concrete (`Log<f32>`, `Log<f64>`)** and `SignedLog` is not `Pod` (it has padding).
- **`Product` and `product_compensated` treat exact `ZERO`/`INFINITY` factors apart from finite ones.** Otherwise `[big, big, ZERO]` (finite logs overflowing past `F::MAX`) panicked as 0·∞ while `[ZERO, big, big]` returned `ZERO`; the result must not depend on order. The plain `Product` keeps a single well-predicted check in its fast loop and switches to a careful path only once its running sum stops being finite.
- **Beyond-range `Display` round-trips exactly up to |log10 x| < 2⁵³;** beyond that not every integer decimal exponent is an `f64`, so a bare power of ten is printed and parsing returns a stored log within an ulp or two. Such values exceed e^(2·10¹⁶).
- **`serde_as_value` takes the logarithm in `f64` before narrowing to `F`,** so `Log<f32>` reads numbers like 1e-50 that an `f32` cannot hold.
- **Parsing uses the float's own parser whenever it yields a normal float** (not merely when the decimal exponent is "safely" inside the range), so `parse` agrees with `from_value` at the edges of the range too.
- **A negative string is rejected if any mantissa digit is non-zero,** even when the value underflows, because the sign, not the rounded magnitude, decides the domain.
- **`From<Log<f32>> for Log<f64>` (and for `SignedLog`) but no narrowing `From`.** Widening is exact; narrowing rounds and can overflow the stored log, so it should be spelled out (`Log::from_ln(x.ln() as f32)`).
- **`libm` is an optional feature that, when enabled, wins over `std`.** It is the conventional way to ask for `no_std` math (as in `num-traits`), and it doubles as the switch for bit-reproducible results; one of the two must be enabled, so a build without a math library fails with an explanatory `compile_error!` rather than linker errors.
- **Reproducibility is promised only with `libm`.** Platform math libraries differ in the last bit (glibc vs. the Windows UCRT measured 0.52 vs 1.25 for `log1mexp`), so with `std` only the documented bounds are promised.
- **The serialized form is frozen from 0.1.0,** with documents in `tests/wire_format.rs`; stored data outlives code.
- **Miri runs with `-Zmiri-deterministic-floats`.** Miri otherwise adds random error to `exp`/`ln` to model imprecise math libraries, which the exact-value tests rightly reject; the job's purpose is the `unsafe` bytemuck impls.
